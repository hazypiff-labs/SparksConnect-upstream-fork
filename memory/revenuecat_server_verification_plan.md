# Server-side RevenueCat Entitlement Verification — Implementation Plan (v3, permissions corrected; for approval; NOT implemented)

Status quo (Phase A, accepted): `X-Premium` is ignored; Premium lane only for `verified_entitlement()` = admin role.
Goal: make `verified_entitlement()` return true for genuinely paying users, from RevenueCat data the server trusts.
Flag `server_entitlements` stays **OFF** until approved. Nothing below is built yet.

## 1. Credential — type, minimum permissions, secure handling (corrected against the official API v2 reference)
- **Type**: RevenueCat **Secret API key v2**, project-scoped (dashboard → Project → *API keys* → "New secret key"), with granular permissions. No v1 key.
- **Permissions per planned endpoint** (verified on revenuecat.com/docs/api-v2/customer/resources):

| Endpoint | Purpose in plan | Required permission | Granted? |
|---|---|---|---|
| `GET /v2/projects/{project_id}/customers/{customer_id}/active_entitlements` | the only call the server needs: is `pro` active, `expires_at` (already reflects store grace periods) | `customer_information:customers:read` | **Yes — the single permission requested** |
| `GET /v2/projects/{project_id}/customers/{customer_id}/subscriptions` | richer diagnostics (`gives_access`, `pending_payment`, `auto_renewal_status`) for the admin "entitlement check" screen | `customer_information:subscriptions:read` | No — optional later, not needed for access decisions |
| `GET /v2/projects/{project_id}/customers/{customer_id}/purchases` | not used | `customer_information:purchases:read` | No |
| `GET /v2/projects/{project_id}/customers/{customer_id}/events` | not used (webhooks deliver events) | `customer_information:customers:read` | covered by the one permission, but not called |
| Any write / `project_configuration:*` / `customer_information:*:write` | — | — | **Never** |

  Correction: the previous draft named `customer_information:subscriptions:read` for `active_entitlements`; the official reference requires `customer_information:customers:read`. The key is therefore created with exactly one read-only permission. Rate limit for this domain: 480 req/min (we need a tiny fraction).
- **Second secret**: webhook **HMAC signing secret**, generated by RevenueCat when signing is enabled on the webhook (shown once).
- **Storage**: backend environment only — `REVENUECAT_SECRET_KEY`, `REVENUECAT_WEBHOOK_SECRET`, `REVENUECAT_PROJECT_ID` (project id not secret). Entered through the deployment panel's environment variables; never in the repo, chat, logs, admin UI or client bundle; startup logs only "configured: yes/no"; test suites stub the HTTP layer. Rotation = create new key → update env → redeploy → delete old key (lookups are a fallback path, so no downtime).

## 1b. Customer-ID mapping (exact)
- The app calls `Purchases.logIn(user.id)` whenever a Date Spark account is signed in (`src/session.tsx`), and `Purchases.logOut()` on sign-out. Therefore for every authenticated user: **RevenueCat `app_user_id` == `users.id` (UUID v4 string)**, and REST `customer_id` == `users.id`.
- Before `logIn`, the SDK uses an anonymous id (`$RCAnonymousID:…`). RevenueCat **aliases** the anonymous id to `users.id` at `logIn`, so a purchase made as a guest that is later followed by sign-in becomes attributable to the account (`original_app_user_id` may be the anonymous id; webhooks carry both `app_user_id` and `original_app_user_id`, plus `aliases`). Purchases made as a guest who **never** signs in have no Date Spark user and are never verifiable server-side (expected: the paywall requires an account).
- Transfers: if a store account restores purchases on a second Date Spark account, RevenueCat emits `TRANSFER` (`transferred_from` / `transferred_to` app_user_ids) — handled by re-fetching both users.
- Server rule: lookups and webhook handling only ever key on `app_user_id` values that **exist in `users` with `deleted_at: null`**; unknown ids are stored for audit but grant nothing.

## 2. Webhook — setup, verification, handling, replay/out-of-order protection
- **Setup (you, in RevenueCat dashboard → Integrations → Webhooks)**: URL `https://<backend>/api/revenuecat/webhook`, environment: Production (+ a separate Sandbox webhook pointing at the preview backend for testing), **enable HMAC signing**, event filter: INITIAL_PURCHASE, RENEWAL, CANCELLATION, UNCANCELLATION, EXPIRATION, BILLING_ISSUE, PRODUCT_CHANGE, SUBSCRIPTION_PAUSED, TRANSFER, SUBSCRIPTION_EXTENDED, TEMPORARY_ENTITLEMENT_GRANT.
- **Verification** (`POST /api/revenuecat/webhook`): read the **raw body**; header `X-RevenueCat-Webhook-Signature: t=<ts>,v1=<hex>`; compute HMAC‑SHA256 over `"{t}.{raw_body}"` with the signing secret; `hmac.compare_digest`; reject if `|now − t| > 5 min` (replay window) → 401. Also accept (but do not require) the legacy `Authorization` header as defence in depth. Reject `environment: SANDBOX` events in production (and vice-versa).
- **Idempotency**: `webhook_events` collection, unique index on `event.id`; duplicate → 200 (acknowledged, not re-applied).
- **Out-of-order**: we never apply events as state transitions. Each event is stored, then the customer's state is **recomputed** from the newest known data: (a) the event's `expiration_at_ms` / `event_timestamp_ms` compared with what we have — older `event_timestamp_ms` than the stored one is recorded but ignored; (b) for any event type that changes access (CANCELLATION with refund, EXPIRATION, BILLING_ISSUE, TRANSFER, PRODUCT_CHANGE) we additionally **re-fetch active entitlements via REST** (RevenueCat's recommended pattern), so the stored state equals RevenueCat's truth regardless of delivery order.
- **Response**: always fast 2xx after persistence; processing errors are logged and retried by RevenueCat (it retries failed deliveries with backoff).

## 3. Entitlement evaluation
`subscriptions` doc per `user_id` (= RevenueCat `app_user_id`, guaranteed by `Purchases.logIn(user.id)`):
`{user_id, entitlement:"pro", active, expires_at, grace_period_expires_at, billing_issue_at, unsubscribe_at, refunded_at, store, environment, source:"webhook"|"lookup", last_event_at, checked_at}`

`verified_entitlement(user)`:
1. Admin role → true (unchanged).
2. Flag OFF → false (Phase A behaviour).
3. Load doc. If missing or `checked_at` > 24 h old → REST lookup (`active_entitlements`, permission `customer_information:customers:read`), persist as `source:"lookup"`.
4. **Active** iff `pro` is present in active entitlements **and** `expires_at > now` (or `grace_period_expires_at > now` when RevenueCat reports a billing grace period). Cases:
   - *Expiration* → `expires_at` passes → inactive automatically even with no event.
   - *Cancellation (auto-renew off)* → stays active until `expires_at` (correct store behaviour), then inactive.
   - *Billing issue* → active during the store grace period (`grace_period_expires_at`), then inactive.
   - *Refund / revocation* (CANCELLATION with `cancel_reason: CUSTOMER_SUPPORT`, or store revocation → EXPIRATION with `expiration_reason`) → REST re-fetch shows no active entitlement → inactive immediately.
   - *Transfer* → the losing user becomes inactive, the gaining user active (both re-fetched).
   - *Product change / paused* → follow REST state.
5. **Fail-closed with protection for real payers** (see §4): if REST is unavailable, use the stored doc if its `expires_at` is in the future (still valid data); if the stored doc expired < 72 h ago and the last known state was active and a lookup is impossible → **grace** (treated active, logged); never grant with no stored evidence.

## 4. Migration & protection of existing legitimate subscribers
- Day 0 (flag OFF): deploy code; register the signed webhooks; confirm test deliveries; admin endpoint `GET /api/admin/entitlement-check?user_id=` shows resolved state side-by-side with the self-reported mirror.
- **Back-fill — identity-safe, no assumptions from counts**. Current data: 59 users, 11 with a self-reported non-free status, 10 self-reported `subscriptions` rows. None of that is proof of identity or payment, so the back-fill does **not** derive entitlement from it:
  1. Candidate set = all non-deleted `users` (59 — small enough; for larger bases: users with any self-reported status **plus** any `app_user_id` seen in webhooks). Using the whole set avoids trusting the self-reported list.
  2. For each candidate, call `active_entitlements` with `customer_id = users.id`. Outcomes: `200` with `pro` → verified active (store `expires_at`, `source:"lookup"`); `200` empty → verified not premium; `404` → RevenueCat has never seen this id (never purchased or purchased only anonymously) → not premium; `401/403` → permission/key problem → abort back-fill (nothing granted); `429` → back off and resume.
  3. Reconciliation report (admin-only, no secrets): for every user, self-reported status vs verified status. Mismatches (self-reported premium but RevenueCat empty/404) are listed for you to review — they are **not** granted. Likely causes: Test-Store sandbox purchases in preview, guest purchases never linked, or forged client reports.
  4. Entitlements are only ever attributed to the exact `users.id` returned as `customer_id`/`app_user_id`; no fuzzy matching on email or device.
- Flip ON (admin flag). Paying users then get the Premium lane from verified data; the app's SDK still gates Premium screens exactly as now.
- **New purchases**: SDK shows Premium instantly; the server learns via webhook within seconds. If a 402 would be returned and the stored state is missing or older than 24 h, the server performs one immediate lookup before denying (bounded to one per request).
- **Recovery path**: (a) "Restore purchases" in the app → SDK sync → RevenueCat emits events; (b) admin "Re-verify" per user → forced lookup; (c) grace window (§3.5) covers outages for users last known active; (d) flag OFF restores Phase A behaviour in seconds.
- Guests: never verified — unchanged policy.

## 5. Effect on the managed RevenueCat integration; reversibility
- Managed provisioning (project, products, entitlement `pro`, offering `default`, public SDK keys, build-config) is **untouched** — we only add a read-only key and a webhook in the same RevenueCat project. The app code path (`react-native-purchases`, Test Store in preview) is unchanged.
- The managed playbook's "client-only gating" rule is intentionally superseded for *limits* only; purchase flows remain SDK-driven.
- **Reversible**: flag OFF → identical to Phase A; delete the webhook and revoke the key → fully back to managed-only. No data migration to undo (the `subscriptions` collection is additive).

## 6. Costs & operations
- RevenueCat REST v2 is included in the plan (current MTR well below the $2.5k free threshold); request volume ≈ purchases/renewals/back-fill + one lookup per 24 h per active payer → negligible, far under rate limits.
- No new paid services; no change to products or pricing.
- Operations: two secrets to rotate (yearly or on incident), webhook health visible in the RevenueCat dashboard, our side logs `webhook_events` and an admin metric "verified premium users / last webhook received at".
